# v55 — восстановление nftset и стабильные обновления кода

Динамический набор `vpn_domains` создаётся как `dst_ip`: DNS добавляет отдельные
адреса, поэтому interval/auto-merge ему не требуется. CIDR-наборы `vpn_subnets`
остаются `dst_net`. Для IPv6 применяется такое же разделение.

На одном OpenWrt 24.10.4 существующий interval-набор был виден, но отвергал
даже прямые `nft add element` с ENOENT. Первопричина внутри kernel/libnftables
не установлена. Эта версия устраняет проверенный способ отказа и добавляет
контроль записи; она не обещает исправить любую ошибку прошивки или блокировку
VPN-сервера провайдером.

## Обновления

- Проверка стабильного кода и списков каждые два часа с распределением минут
  между роутерами. Проверка nftset каждые пять минут.
- Загружается небольшой manifest; архив кода скачивается только при новой
  версии. В v55 архив содержит 30 исполняемых скриптов, около 25 КБ в gzip.
- Контроль HTTPS-сертификата, SHA-256, состава/размера архива и синтаксиса.
- Фиксированный список разрешённых путей. Ключи, `/etc/config/network`, конфиги
  туннелей, пакеты, ядро и прошивка в архив не входят и не обновляются.
- Перед заменой — одна резервная копия предыдущего runtime, firewall и cron.
  Ошибка локальной проверки вызывает откат. Незавершённая замена обнаруживается
  при следующем запуске. Неудачный релиз блокируется до ручного повтора или
  публикации следующей версии.
- Код не понижается автоматически. При недостатке свободной flash/RAM обновление
  откладывается. Параллельные задания защищены блокировками.
- Исправлено ложное сообщение об успехе при неуспешном `--update`.

## Списки и диагностика

- Неизменившиеся списки не перезапускают DNS/firewall и не перезаписывают cache.
- Изменения применяются одной транзакцией списков. HTML, ошибочный ответ,
  неуспешная загрузка или ошибка применения сохраняют предыдущие файлы.
- Проверяется настоящая операция добавления/удаления элемента nftset.
- При замене динамического набора сохраняются его существующие адреса, чтобы
  DNS-кэш устройств не оставил работающие соединения без маршрута.
- Миграция больших интервалов и неоднозначных/чужих правил не выполняется
  вслепую: возвращается ошибка для ручной диагностики.

## Команды

```sh
rw updates status
rw updates check
rw updates off
rw updates on
rw updates rollback
rw health
```

`off` отключает только автоматическое обновление кода, списки обновляются дальше.
`check` — явный повтор проверки и установки, в том числе ранее неудачного релиза.
Откат относится к автоматическому runtime-обновлению; полная ручная переустановка
пакетов/туннеля установщиком не стала транзакционной.

## Уже установленные роутеры

Текущие установки, чья cron-задача скачивает `update.sh --auto`, увидят новую
версию при следующем старом запуске (у v54 обычно 02:00). После успешной миграции
расписание станет двухчасовым. Публикация не означает мгновенное обновление всех
роутеров, и GitHub не сообщает, какой роутер уже обновился.

Самые старые установки с одним `getdomains`, без загрузки `update.sh`, сами код
не получат. Им нужен один ручной запуск новой версии. Если HTTPS-сертификат не
проверяется, код не устанавливается: сначала проверяют время и CA bundle, без
отключения проверки сертификата. Первый legacy-вход ещё выполняется старым
загрузчиком; новый безопасный загрузчик заменяет его после успешной миграции.

## Разработчику

Правки в `main` сами по себе не являются стабильным релизом. Для распространения
исправлений повышаются `version` и `PROJECT_VERSION`, выполняется
`python3 tools/build_release.py`, проходят тесты, затем публикуются source,
`releases/stable.manifest` и соответствующий неизменяемый архив одним commit.
SHA-256 проверяет целостность; manifest доверяется по HTTPS и правам владельца
репозитория. Отдельной цифровой подписи релиза здесь нет.

Проверки: `tests/Dockerfile` и `.github/workflows/stability.yml`. Тесты запускаются
только в одноразовом контейнере без сети с собственной network namespace;
используется реальный nftables. Прямо на рабочем роутере тестовый набор не запускают.
