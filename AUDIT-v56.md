# Проверка устойчивости RouteWolf v56

Проверены shell-код обновления и маршрутизации, данные списков и сохранение
конфигурации. Это не полный аудит ядра OpenWrt, драйверов или сторонних пакетов.
Выводы ниже основаны на коде и воспроизводимых тестах, а не на предположении,
что обычный интернет у всех пользователей сейчас не работает.

| Находка | Последствие | Изменение |
|---|---|---|
| В v55 задания запускались каждые два часа | Расписание не соответствовало требованию владельца | Независимые ежедневные задания 02:00/03:00 |
| Код проверял floating manifest в main | Нельзя было управлять выпуском только через GitHub Releases | Опубликованные стабильные Releases; tagged asset для архива |
| Watchdog после неуспешного теста повторно вызывал route helper | UP-интерфейс мог снова получить маршрут для отмеченного трафика | Временный unhealthy-маркер; WAN по-прежнему доступен |
| Маркер pending удалялся даже при ошибке восстановления | Следующий запуск мог не повторить recovery | Pending сохраняется до успешного восстановления |
| Часть загрузчиков использовала отключённую проверку TLS | Посредник мог подменить загружаемый скрипт при ручном обновлении | Проверка сертификатов и ограниченные загрузки |
| Domain list принимал server/ipset/nftset к произвольному набору | Ошибка или подмена списка меняла DNS/чужую ACL-таблицу | Только принадлежащие RouteWolf nftset-директивы |
| URL записывался в sourced-конфиг без экранирования кавычки | Специально сформированный URL, вставленный администратором, мог стать shell-кодом | Literal quoting и тест инъекции; это не unauthenticated remote exploit |
| Проверка RAM выполнялась слишком поздно | На загруженном слабом устройстве staging мог ухудшить ситуацию | Проверка ресурсов до скачивания и ограничение файла/распаковки |

## Что подтверждают тесты маршрутизации

В контейнере без внешней сети создаются отдельные WAN и VPN dummy-интерфейсы,
настоящие `ip rule`, policy table и nftables. Проверяется выбор маршрута для
обычных и помеченных пакетов. Недоступность удалённого сервиса моделируется
ошибкой проверочного клиента; WireGuard peer в интернете намеренно не отключается.

Дополнительно запускаются реальные опубликованные v55-скрипты как отрицательный
контроль: воспроизводится повторное добавление policy route, при этом обычный WAN
остаётся доступен. Поэтому находка не означает, что у владельца роутера пропадал
весь интернет, и не отменяет его наблюдений о работающем fail-open.

## DNS и периодические отказы YouTube

Доменная маршрутизация зависит от DNS-ответов, которые видит dnsmasq роутера.
Если настроенный upstream DNS недоступен, нельзя сделать вывод о блокировке
VPN-сервера только по отсутствию загрузки YouTube. Отдельно проверяются DNS,
запись адресов в nftset, передача через туннель и доступность видеосервисов.
Автообновление не заменяет DNS Google/Cloudflare и не внедряет новый DNS-сервер.

Сегодняшний зафиксированный отказ — запись в существующий interval nftset при
наличии DNS-ответов. Его устранение в v55/v56 не доказывает, что любой похожий
отказ на другом роутере имеет ту же причину. В частности, драйвер/прошивка,
доступность DNS, блокировка адреса и клиентский DNS-кэш проверяются отдельно.

## Оставшиеся ограничения

- Неизвестные/чужие firewall-правила не переписываются вслепую; обновление может
  остановиться с диагностикой вместо рискованной переделки маршрутизации.
- При отсутствии совместимых fw4/nftables/sha256sum обновление кода откладывается.
- 5 МиБ свободной flash проверены как сценарий в тестовой среде; это не натурный
  тест каждого устройства с 16 МБ flash. На устройстве проверяется реальный резерв.
- Запись файлов и аппаратный сбой питания не являются одной атомарной операцией:
  journal/recovery уменьшают риск, но не дают абсолютной гарантии от повреждения flash.
- SHA-256 подтверждает целостность относительно manifest по HTTPS; отдельной
  офлайн-подписи релиза нет. Доступ владельца к GitHub остаётся доверенной границей.
